# FretWizard Accounts & Sync — Design

**Date:** 2026-10-01
**Status:** Approved in brainstorming, pending written-spec review
**Repos:** `fretWizard-service/` (backend, Express + Prisma + SQL Server) and `fret-wizard/` (frontend, Vue 3 + Pinia). Sibling folders, separate git repos.

## 1. Goal

Let a FretWizard user create an account (email + password, or Google) and have their Library, their Scale/Chord page stacks, and their Chord Progression follow them across devices. The app keeps working without an account exactly as it does today; on first login, whatever the browser has saved is imported into the account.

Success means:

- A user can sign up and log in with email + password, or with Google.
- A logged-in user's Library cards, Scale stack, Chord stack and Chord Progression are stored by the backend and load on any device.
- A guest's browser data is imported into the account on login without losing anything.
- Guests see no change in behaviour.

## 2. Decisions

| # | Question | Decision |
|---|---|---|
| D1 | Guest mode | Login optional. On transition to logged-in, the browser's data is imported into the account. |
| D2 | Hosting | Not decided. Design for frontend and API on different sites: tokens are returned in response bodies; the refresh token lives in `localStorage`. |
| D3 | Google login on an email that already has a password account | Link the Google identity to the existing account and clear the password (it was never proven to belong to the email owner). Revoke the account's existing sessions. |
| D4 | Username | Display name only. Not unique. Login is by email. Google sign-ups take their Google name. |
| D5 | Existing database | Dev data only. Reset; replace the migration history with one fresh migration. |
| D6 | Scope | Backend **and** frontend integration in one spec and plan. |
| D7 | What syncs | Library, Scale stack, Chord stack, Chord Progression. Theme stays per device. |
| D8 | Library vs page configs storage | **Separate tables**, one database row per fretboard (normalised columns), not Library-with-a-flag and not JSON documents. |
| D9 | Fretboard row ownership | Two tables with identical fretboard columns: `CardFretboard` and `WorkspaceFretboard`. Everything stays expressible in `schema.prisma` (no hand-written CHECK constraints, filtered indexes or NO ACTION foreign keys). |
| D10 | `HighlightNotes` | Kept as a small JSON array string, validated against the 12 degrees. The one exception to "a column per setting". |
| D11 | Session length | Refresh tokens expire 7 days after they are issued; each refresh issues a new one (sliding 7 days). |
| D12 | Import conflicts | Cards are always appended. Stacks and progression are applied only where the account has nothing saved; otherwise the account wins. |
| D13 | Backend layering | Thin routes → services → Prisma. Shared fretboard mapper. |
| D14 | Tests | Backend: `node:test` + `supertest` against a real SQL Server test database. Frontend: Vitest for logic; manual browser pass for UI. |
| D15 | Auth UI | Top-bar "Sign in" button opening a modal, not a separate page. |

## 3. Scope

**In scope**

- Email sign-up, email login, Google sign-in (sign-up and login through one endpoint), refresh, logout, current-user profile (read, change display name).
- Library cards: list, create, rename, replace stack, delete.
- Workspaces (Scale and Chord page stacks): read, replace.
- Chord Progression: read, replace.
- Guest-data import.
- Fixing the existing backend's security and structure problems (Section 7.1).
- Frontend: auth store, HTTP client, sign-in UI, switching persistence between `localStorage` and the API at runtime, import on login, logout.

**Out of scope** (later work)

- Password reset, email verification, changing email or password (all need an email provider).
- Account deletion, admin user management.
- Other OAuth providers. The `UserLogin` table is ready for them; no endpoint work now.
- Theme sync.
- Offline editing, conflict resolution. Saves are last-write-wins.
- Hosting and deployment.
- Sharing cards between users.

## 4. Data model

One fresh Prisma migration (`init`) replaces `prisma/migrations/20260422095044_user`. The `Card` and `Fretboard` tables are dropped.

Conventions kept from the existing schema: PascalCase table and column names, `UNIQUEIDENTIFIER` keys, named constraints (`PK_…`, `FK_…`, `UQ_…`, `IX_…`), `CreatedDate`/`ModifiedDate`. IDs are generated by Prisma (`@default(uuid())`).

Notes that apply throughout:

- **No database enums.** Prisma does not support enums on SQL Server. `Setup`, `Pattern`, `Tonality`, `Accidental`, `ChordView`, `Provider` are strings, validated by the API (Section 6.4).
- **`KeyName`, not `Key`.** `KEY` is a reserved word in T-SQL. Prisma brackets it, but any hand-written SQL would trip over it.
- **`StringLowE` / `StringHighE`.** The frontend's `currentStrings.E` and `currentStrings.e` cannot become `StringE` and `Stringe`: SQL Server's default collation is case-insensitive, so the names would collide.
- **No `currentSetup` per fretboard row.** It always equals the parent's setup and is filled in on read.
- **Cascades.** Every child table is reachable from `User` by exactly one cascade path. SQL Server rejects a table reachable by two cascade paths (error 1785), which is why fretboard rows live in two tables (D9).
- **Saving a stack** replaces it: in one transaction, delete the parent's fretboard rows and insert the new ones with `Position` 0..n-1. Rows are never updated individually, so fretboard row IDs never leave the server.

## 5. Authentication

### 5.1 Email sign-up — `POST /auth/signup`

Request `{ username, email, password }`.

1. Validate (Section 6.4). `email` is trimmed and lowercased; `username` is trimmed.
2. If any user has that email (password or Google account) → `409 CONFLICT` "An account with this email already exists".
3. Hash the password with bcrypt, cost 12. Create the user.
4. Issue tokens in a new family (5.4). Respond `201` with the auth response.

### 5.2 Email login — `POST /auth/login`

Request `{ email, password }`.

1. Validate; normalise the email.
2. Look up the user. If there is no user, the user is inactive, or `PasswordHash` is `NULL`, still run `bcrypt.compare` against a fixed dummy hash (so response time doesn't reveal which emails exist), then respond `401 UNAUTHORIZED` "Invalid email or password".
3. If the password is wrong → the same `401`.
4. Delete this user's refresh tokens whose `ExpiresAt` has passed. Issue tokens in a new family. Respond `200`.

### 5.3 Google — `POST /auth/google`

Request `{ idToken }`: the credential produced by the Google Identity Services button on the frontend.

1. Verify with `google-auth-library` `OAuth2Client.verifyIdToken({ idToken, audience: GOOGLE_CLIENT_ID })`. This checks signature, issuer, audience and expiry. Any failure → `401 UNAUTHORIZED` "Google sign-in failed".
2. Require `payload.email_verified === true`, else the same `401`.
3. If a `UserLogin` row matches `(Provider 'google', ProviderUserId payload.sub)` → that user. If inactive → `401`.
4. Else, if a user has `payload.email` (lowercased) → **link**, in one transaction:
   - insert `UserLogin('google', sub)`,
   - set `PasswordHash = NULL`,
   - set `RevokedAt = now` on all of that user's unrevoked refresh tokens.
   If that user is inactive → `401` (no link).
5. Else **create** a user: `Username` = `payload.name` trimmed and cut to 100 characters, or the part of the email before `@` if `name` is missing; `PasswordHash = NULL`; plus the `UserLogin` row.
6. Delete expired refresh tokens, issue tokens in a new family, respond `200` with the auth response plus `isNewUser` (`true` only in case 5).

`verifyIdToken` is wrapped in `services/google.js` exposing `verify(idToken) → { sub, email, emailVerified, name }`, and passed to `createApp`, so tests use a fake.

### 5.4 Tokens

**Access token.** JWT, HS256, payload `{ sub: userId }`, expires in 15 minutes, signed with `JWT_SECRET`. Verification pins `algorithms: ['HS256']`. The `requireAuth` middleware reads `Authorization: Bearer <token>`, sets `req.userId`, and responds `401 UNAUTHORIZED` for a missing, malformed, invalid or expired token. It does not touch the database, so a deactivated user keeps access for at most 15 minutes.

**Refresh token.** `crypto.randomBytes(32).toString('base64url')`. Only `TokenHash` (SHA-256, lowercase hex, 64 characters) is stored. `ExpiresAt` = issue time + 7 days. Login, sign-up and Google sign-in each start a new `FamilyId`.

**Refresh — `POST /auth/refresh`**, request `{ refreshToken }`:

1. Hash it and look it up. Not found → `401`.
2. `RevokedAt` is set → **reuse detected**: set `RevokedAt = now` on every unrevoked token in that family, respond `401`.
3. `ExpiresAt` has passed → `401`.
4. User missing or inactive → revoke the family, `401`.
5. In one transaction: set `RevokedAt = now` on the presented token and insert a new token with the same `FamilyId` and `ExpiresAt` = now + 7 days.
6. Respond `200 { accessToken, refreshToken }`.

Revoked tokens are kept until they expire so that reuse can be detected; they are deleted by the cleanup in 5.2 and 5.3.

**Logout — `POST /auth/logout`**, request `{ refreshToken }`: if the token is found, revoke its whole family. Always respond `204`, even if the token is unknown.

**Auth response** (sign-up, login, Google):

```json
{
  "accessToken": "…",
  "refreshToken": "…",
  "user": { "id": "uuid", "email": "jo@example.com", "username": "Jo" },
  "isNewUser": false
}
```

`isNewUser` is present only on `/auth/google`.

### 5.5 Rate limits

`express-rate-limit`, keyed by client IP:

- `/auth/signup`, `/auth/login`, `/auth/google`: 10 requests per minute.
- `/auth/refresh`: 60 requests per minute.

Exceeding a limit → `429 RATE_LIMITED`. `TRUST_PROXY` configures Express's `trust proxy` so IPs are correct behind a hosting proxy.

### 5.6 Accepted risks

- `409` on sign-up reveals that an email has an account. Accepted for this app.
- The refresh token in `localStorage` is readable by injected script (XSS). Mitigated by rotation, reuse detection and the 7-day expiry. Revisit with an `httpOnly` cookie once the frontend and API share a site (D2).

## 6. API contract

### 6.1 Conventions

- JSON field names on the wire are **camelCase**. The database stays PascalCase; each service converts in one place. (The existing auth routes' `Email`/`Password` fields change to `email`/`password`; nothing calls them yet.)
- Stacks on the wire use the frontend's `FretboardData` shape exactly, so the frontend needs no conversion.
- `createdAt` on a library card is epoch **milliseconds** (a number), matching the frontend's `LibraryCard`.
- Every query for a user's data includes `UserId` in its `where` clause. Another user's card, or an ID that is not a UUID, responds `404 NOT_FOUND`. This never reveals whether the card exists.
- Request bodies are limited to 1 MB (`express.json({ limit: '1mb' })`).

### 6.2 Errors

Every error, including unknown routes and server errors, is JSON:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid request body", "details": [{ "path": "fretboards.0.fretAmount", "message": "Must be between 12 and 24" }] } }
```

| Code | Status | When |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Body or parameters fail validation. `details` lists each field. |
| `UNAUTHORIZED` | 401 | Missing or invalid credentials or token. |
| `NOT_FOUND` | 404 | Unknown route, or a resource that doesn't exist or isn't yours. |
| `CONFLICT` | 409 | Email already registered. Also Prisma `P2002` (unique constraint). |
| `LIMIT_EXCEEDED` | 409 | Would exceed a per-user limit (Section 6.5). |
| `RATE_LIMITED` | 429 | Rate limit hit. |
| `INTERNAL` | 500 | Anything else. The message is generic; no stack trace is sent. |

### 6.3 Endpoints

🔒 = requires `Authorization: Bearer <accessToken>`.

| Method and path | Request body | Success response |
|---|---|---|
| `POST /auth/signup` | `{ username, email, password }` | `201` auth response |
| `POST /auth/login` | `{ email, password }` | `200` auth response |
| `POST /auth/google` | `{ idToken }` | `200` auth response + `isNewUser` |
| `POST /auth/refresh` | `{ refreshToken }` | `200 { accessToken, refreshToken }` |
| `POST /auth/logout` | `{ refreshToken }` | `204` |
| 🔒 `GET /me` | — | `200 User` |
| 🔒 `PATCH /me` | `{ username }` | `200 User` |
| 🔒 `GET /library-cards` | — | `200 LibraryCard[]`, oldest first |
| 🔒 `POST /library-cards` | `{ name, setup, fretboards }` | `201 LibraryCard` |
| 🔒 `PATCH /library-cards/:id` | `{ name?, fretboards? }` (at least one) | `200 LibraryCard` |
| 🔒 `DELETE /library-cards/:id` | — | `204` |
| 🔒 `GET /workspaces/:setup` | — | `200 { fretboards }`, or `404` if never saved |
| 🔒 `PUT /workspaces/:setup` | `{ fretboards }` | `204` |
| 🔒 `GET /chord-progression` | — | `200 ChordProgression`, or `404` if never saved |

| 🔒 `POST /me/import` | `ImportRequest` | `200 ImportResult` |

`:setup` is `scale` or `chord` (lowercase in the URL; stored as `Scale` / `Chord`). Any other value → `404`.

Shapes:

```ts
type User = { id: string; email: string; username: string }

type LibraryCard = {
  id: string
  name: string
  setup: 'Scale' | 'Chord'
  fretboards: FretboardData[]
  createdAt: number            // epoch ms
}

type FretboardData = {
  fretAmount: number
  currentKey: string
  currentSetup?: 'Scale' | 'Chord'   // ignored on input, always present in responses
  currentPattern: string
  currentTonality: 'Major' | 'Minor'
  currentAccidental: 'sharp' | 'flat'
  currentHighlightNotes: string[]
  currentCAGED: { CShape: boolean; AShape: boolean; GShape: boolean; EShape: boolean; DShape: boolean }
  currentStrings: { E: boolean; A: boolean; D: boolean; G: boolean; B: boolean; e: boolean }
  currentChordPosition: number
  chordView?: 'shapes' | 'fingering'
}

type ChordProgression = {
  key: string
  tonality: 'Major' | 'Minor'
  progression: { id: string; degree: number }[]
}

type ImportRequest = {
  libraryCards?: { name: string; setup: 'Scale' | 'Chord'; fretboards: FretboardData[] }[]
  workspaces?: { scale?: { fretboards: FretboardData[] }; chord?: { fretboards: FretboardData[] } }
  chordProgression?: ChordProgression
}

type ImportResult = {
  importedCards: number
  appliedWorkspaces: ('scale' | 'chord')[]
  appliedChordProgression: boolean
}
```

On `PUT /chord-progression` (and in an import), incoming progression `id`s are ignored; the server generates new ones, returned by the next `GET`. The frontend uses them only as list keys.

### 6.4 Validation

`zod` schemas in `validation/`. Allowed values mirror the frontend's `src/lib/music-theory/constants.ts`.

| Field | Rule |
|---|---|
| `username` | String, trimmed, 1–100 characters |
| `email` | Valid email, at most 255 characters, trimmed and lowercased |
| `password` | String, at least 8 characters, at most 72 **bytes** (bcrypt ignores anything past 72 bytes) |
| `name` (card) | String, trimmed, 1–100 characters |
| `setup` | `Scale` \| `Chord` |
| `fretboards` | Array of 1–50 `FretboardData` |
| `fretAmount` | Integer 12–24 |
| `currentKey` | One of `C C♯ D D♯ E F F♯ G G♯ A A♯ B D♭ E♭ G♭ A♭ B♭` |
| `currentPattern` | One of `Pentatonic Scale`, `Blue Scale`, `Diatonic Scale`, `Chromatic Scale`, `Power Chord`, `Triad`, `Seventh Chord`, `Add9 Chord`, `Add11 Chord`, `Add13 Chord`, `Dominant Chord` |
| `currentTonality` | `Major` \| `Minor` |
| `currentAccidental` | `sharp` \| `flat` |
| `currentHighlightNotes` | 0–12 unique values from `roots`, `minor seconds`, `seconds`, `minor thirds`, `thirds`, `fourths`, `tritones`, `fifths`, `minor sixths`, `sixths`, `minor sevenths`, `sevenths` |
| `currentCAGED` | Object; all five boolean keys `CShape AShape GShape EShape DShape` required |
| `currentStrings` | Object; all six boolean keys `E A D G B e` required |
| `currentChordPosition` | Integer 0–23 |
| `chordView` | Optional, `shapes` \| `fingering` |
| progression `key` | For `Major`: one of `C G D A E B F♯ D♭ A♭ E♭ B♭ F`. For `Minor`: one of `A E B F♯ C♯ G♯ E♭ B♭ F C G D`. |
| progression `degree` | Integer 0–6 |
| `progression` | Array of 0–100 items |
| `libraryCards` (import) | Array of 0–200 cards |

Unknown fields, at any level including inside `currentCAGED` and `currentStrings`, are stripped rather than rejected (there is no column for them). Adding a field to `FretboardData` therefore requires a backend change: a column in both fretboard models, the mapper, and the schema.

### 6.5 Limits

- 200 library cards per user. `POST /library-cards` at the limit, or an import that would exceed it → `409 LIMIT_EXCEEDED`; nothing is created.
- 50 fretboards per stack, 100 chords per progression (enforced by validation).

### 6.6 Import semantics — `POST /me/import`

- Validated as a whole first. Any invalid item → `400`, nothing saved.
- Runs in one transaction.
- Every card in `libraryCards` is created with a new server ID, in array order. Existing cards are never touched.
- `workspaces.scale` / `workspaces.chord` is saved only if the account has no rows for that setup; otherwise it is skipped (the account wins).
- `chordProgression` is saved only if the account has none; otherwise skipped.
- The result reports exactly what was applied.

## 7. Backend structure

### 7.1 Existing problems fixed by this work

- Only the `User` table has a migration; `Card`, `Fretboard` and `RefreshToken` are in the schema but not in any migration.
- `/users` has no authentication: anyone can list, create, change or delete users. **Removed.**
- `/cards` and `/fretboards` don't check ownership, and `POST /cards` trusts a `UserId` from the request body. **Replaced.**
- `Username` is `NCHAR(100)` (space-padded). `PasswordHash` is required, which blocks Google-only users.
- Refresh tokens are JWTs stored in plain text.
- The auth middleware answers `403` for an expired token.
- No CORS, so a browser on another origin can't call the API.
- Errors render the Jade HTML error page.
- Each route file creates its own `PrismaClient`.
- No input validation, no tests.

### 7.2 Dependencies

- **Keep:** `express` (bump `~4.16.1` → `^4.21.2` for security fixes), `@prisma/client` + `prisma` 5.22, `bcrypt`, `jsonwebtoken`, `swagger-jsdoc`, `swagger-ui-express`, `morgan`, `dotenv`, `debug`.
- **Add:** `google-auth-library`, `zod`, `cors`, `express-rate-limit`. Dev: `supertest`.
- **Remove:** `jade`, `cookie-parser`, `http-errors`.

## 8. Frontend integration (`fret-wizard/`)

### 8.1 Configuration

- `VITE_API_BASE_URL` and `VITE_GOOGLE_CLIENT_ID`, in `.env.development` (`http://localhost:3000`, plus the client ID). `.env.production` leaves `VITE_API_BASE_URL` unset until the API is hosted.
- When `VITE_API_BASE_URL` is unset, every account feature is hidden and the app is guest-only, exactly as today. GitHub Pages deploys keep working.
- The hard-coded `BASE_URL = 'http://localhost:3000'` in `apiAdapter.ts` is removed.

### 8.2 Auth store — `src/stores/useAuthStore.ts`

- State: `user: User | null`, `accessToken: string | null` (memory only), `status: 'restoring' | 'guest' | 'authenticated'`, `sessionVersion: number`.
- The refresh token is stored in `localStorage` under `refreshToken`.
- `restoreSession()` runs once on app start. With a refresh token: `/auth/refresh` → `GET /me` → `authenticated`. On `401`, delete the stored token → `guest`. On a network error, keep the token → `guest` for this page load (it is retried on the next load).
- `signup`, `login`, `loginWithGoogle(idToken)`, `logout`.
- Every move to `authenticated` (login, sign-up, Google, or a successful restore) runs the guest-data import (8.5) and then increments `sessionVersion`. `logout` also increments it.
- A `window` `storage` listener: when another tab removes `refreshToken`, this tab drops to `guest` and increments `sessionVersion`.
- `DefaultLayout` renders the pages only once `status !== 'restoring'`.

### 8.3 HTTP client — `src/services/http.ts`

- A small `fetch` wrapper: base URL, JSON body and headers, `Authorization: Bearer` when an access token exists, and errors thrown as `ApiError { status, code, message, details }` built from the error body.
- On `401` from any endpoint except `/auth/*`: refresh once, retry the request once. If the refresh fails, clear the tokens and drop to `guest`.
- **Refresh is serialised across tabs** with `navigator.locks.request('fw-refresh', …)`. Inside the lock the refresh token is **re-read from `localStorage`**, so a token another tab just rotated is never sent again (which would trigger reuse detection and log the user out). Within one tab, concurrent `401`s share one in-flight refresh promise. Where `navigator.locks` is missing, only the in-tab de-duplication applies.

### 8.4 Persistence switch

- `customizerService.ts` replaces the compile-time `USE_API` constant with a runtime check: `useAuthStore().status === 'authenticated'`. Theme always uses `localStorage`.
- `apiAdapter.ts` is rewritten against the endpoints in Section 6.3.
- Library operations become per-card in both adapters and in the service: `fetchLibraryCards`, `createLibraryCard(input) → LibraryCard`, `updateLibraryCard(id, patch) → LibraryCard`, `deleteLibraryCard(id)`. The `localStorage` adapter implements them by reading, changing and writing back the array, as today. `saveLibraryCards(cards)` is removed.
- `useLibraryStore` calls the per-card operations and keeps the card the service returns (in API mode, its ID comes from the server). It gains `reset()`.
- In API mode, workspace saves (`saveFretboards`) and chord progression saves are debounced with `lodash` `debounce` (800 ms, trailing). The service exposes `flushPendingSaves()`. `DefaultLayout` calls it before `saveActiveCard()` in `switchView` and `onLoadCard`, so the active card is updated from the latest stack.
- `saveCurrentFretboard` does nothing in API mode. It only duplicates `stack[selectedIndex]` and has no endpoint.

### 8.5 Guest-data import — `src/services/guestData.ts`

- `collectGuestData()` reads `libraryCards`, `scaleFretboardList`, `chordFretboardList` and `chordProgression` from `localStorage` through the existing local adapter, including its legacy-format handling. It returns an `ImportRequest`, or `null` if none of those keys exist.
- `clearGuestData()` removes those keys and their companions `scaleCurrentFretboard` and `chordCurrentFretboard`.
- On every move to `authenticated`: if `collectGuestData()` is not `null` → `POST /me/import`.
  - On success → `clearGuestData()`.
  - On failure → keep the local data, show a small notice "We couldn't import the data saved in this browser.", and stay logged in. The next move to `authenticated` tries again.
- Then increment `sessionVersion`.

### 8.6 Session changes and remounting

- `DefaultLayout` keys `FretboardPage`, `ChordProgressionPage` and `LibraryPage` on `sessionVersion`, so they remount and reload from the active persistence when the session changes.
- On a `sessionVersion` change, `useLibraryStore.reset()` clears cards and `activeCardId`, then reloads.
- **Logout:** `POST /auth/logout` (errors ignored), remove the refresh token, clear the access token and user, `status = 'guest'`, increment `sessionVersion`. The app then shows whatever `localStorage` holds, which is empty after an import, so the pages show defaults.

### 8.7 UI

- **Top bar**, beside the theme switch: a "Sign in" button for guests; when signed in, the display name and a "Log out" action. Hidden when `VITE_API_BASE_URL` is unset.
- **`src/components/AuthModal.vue`** (Bootstrap modal, already a dependency):
  - "Log in" and "Sign up" tabs. Sign up asks for display name, email and password; log in asks for email and password.
  - A "Sign in with Google" button. The Google Identity Services script (`https://accounts.google.com/gsi/client`) loads on demand when the modal opens; `google.accounts.id.initialize({ client_id, callback })` and `renderButton` draw the button; the callback calls `loginWithGoogle(credential)`.
  - Minimal type declarations for `google.accounts.id` in `src/types/gsi.d.ts`.
  - Errors by code: `409 CONFLICT` → "An account with this email already exists"; `401` → "Invalid email or password"; `400` → each `details` message beside its field; `429` → "Too many attempts. Try again in a minute."; anything else → "Something went wrong. Try again."
- Guest mode has no prompts or nags.

### 8.8 Cleanup

- Remove the `json-server` npm script. It is unused and clashes with the backend on port 3000.
- Update the frontend `CLAUDE.md`: backend on port 3000, the new env variables, auth and sync architecture, `npm test`.
